I have agents, mostly running in Claude Code, Anthropic's coding agent, doing real work across my projects. They write code, file notes, review each other's work and draw figures for my site, and a lot of it is good. The trouble is the work that was good once and different the next time, because an agent guessed, ignored a rule, forgot a decision, or wasn't called when it should have been.

None of that was the model being stupid. Traced back, each failure ends in the same place, a decision that lived only in written instructions, where nothing could hold it.

I come from chip design, and chip design met this problem long before agents did. A foundry, the factory that makes chips, ships a **rule deck** with thousands of geometry rules, and every chip layout must pass all of them before the factory will build it. The designer never edits the deck. A program checks every layout against it, every time, and a rule that can't be met needs a named person to sign a waiver. So the designer's judgment is kept for the part no deck can decide, which is the architecture. A judge the builder can't touch, and judgment kept for what needs it. That's the shape this article builds for agents. Here it is in one place before it's built piece by piece.

- A **rule** is one line of guidance, kept with the failure that created it.
- A **check** is code that decides a rule, with the same verdict every time.
- The **kernel** is the code the agent builds with.
- **Examples** of good and bad output set the quality bar.
- A **playbook** packs the steps, rules, kernel, checks and examples for one job.
- An **agent** owns several playbooks and keeps what it learns in files.
- **Workers** each take one narrow brief, and a script starts and collects them.

The article ends with how someone who doesn't write code can use all of it.

## What went wrong first

Toyota's engineers have a method for finding a cause you can fix. You ask "why?" five times, and each answer feeds the next question. I put the two chains below together afterwards, from the records of the failures.

**Too many agents.**

| Ask | Answer |
|---|---|
| Why did the work drift? | Each agent had part of the context and its own copy of the rules. |
| Why its own copy? | A new topic got a new agent. |
| Why a new agent per topic? | Agent count is an easy number to grow, and nothing said when not to. |
| Why did nothing say? | There was no test for "this needs a new agent". |
| Why no test? | A topic has no boundary a program can check. |
| **So** | Split agents at a boundary you can check, such as what it may do, what data it reads and who owns it, never by topic. |

What I wrote in my notes at the time still holds, that "quality is not the number of agents but the playbooks in an agent and how its rules are defined". A **playbook**, for now, is a packaged procedure an agent follows for one kind of job. It gets built up properly further down.

**The right agent wasn't called.** An agent picks which of its procedures to use from a one-line description of each.

| Ask | Answer |
|---|---|
| Why wasn't the procedure used? | The agent picked a different one, or none. |
| Why? | It chose from the one-line descriptions. |
| Why did the description fail? | Too broad, and the agent read it as a summary and skipped the steps. Too narrow or vague, and it never matched. |
| Why was it written like that? | It was written to describe the procedure, not to be matched against. |
| Why? | Nobody treated the description as the trigger it is. |
| **So** | A description says only when to use it ("Use when ..."), and fixed events such as a saved change, a schedule or a request for review start an agent through a hook, a script the tools run at that event, not through the agent's judgment. |

Other failures followed shorter chains to the same kind of root.

| What went wrong | What happened | What answers it |
|---|---|---|
| An agent guessed | An agent's question that blocked the work went unanswered for a day. Then the agent acted on a guess it never wrote down, and the guess was wrong | A written list of when to stop and ask, and every guess recorded with what it would cost if wrong |
| An agent forgot | An audit of 22 past sessions found about 17 things we had agreed with no entry in the project's task list. They lived in a note in a temporary folder, in agent memory or in the chat | A fixed place in files for what an agent learns, and every decision written as a work item |
| A rule in the prompt didn't hold | 19 of 20 runs still kept a backup value the rules forbade | A check, a script that decides the rule every time |
| A report trusted the wrong signal | A run was reported as passed because the command printed a success message, while the program had really failed | Results read from the real exit code, never from printed text |

An exit code is the number a program hands back when it finishes, and 0 means it succeeded. The simplest fix in that table, reading the real exit code, is a single rule, so that's where the building starts.

## A rule, and the check it turns into

A **rule** is one line of guidance with its reasons attached. Mine carry an id, the rule, why it exists, the case that created it, and how sure I am of it. Here is a real one from my rules for building agents.

| Rule | Why | Case that created it | Evidence | Could a script check it? |
|---|---|---|---|---|
| Read a run's result from its output file and its real exit code, never from the task status or from text the command echoed. | The status only says the run ended, not that the work passed. | A background run was reported as a success because the command echoed the code. The real exit was 1. | adopted (confirmed) | yes, the runner can store the real exit code where the report reads it |

The case ties the rule to a real failure, so the list grows only as fast as real failures do, and a rule can be retired once its case passes without it. The evidence says whether I've confirmed the rule or it's still on trial. A rule seen in one project stays on trial, and a trial rule is still followed and reported where it doesn't fit. When a second project of mine hits the same failure and reports it, the rule becomes a candidate, and then I adopt it or drop it. This one was reported by two projects on the same day, and I adopted it then.

The column that matters most is the last one. "Could a script check it?" is asked of every rule, and when the answer is yes, the rule's job is to leave the list and become a check.

A **prompt** is everything the model reads before it acts, the ask itself plus whatever rules and examples come with it. A rule in a prompt is only a request. My agents don't get one long prompt with every rule in it. They read in layers, the way you'd read a manual, starting from a one-line index of what they can do, opening the playbook for the job in hand, and reading a rule for one step only when they reach that step. Then a check decides whether the result passes, and a failure goes back for another try.

<Diagram id="agents-prompt-loop" />

My rule experiments measured how good a request can be. The model wrote the same small program again and again, and code I'd first tested on deliberately broken samples scored each run out of 10.

| Rules in the prompt | Runs | Average score out of 10 |
|---|---|---|
| none | 10 | 7.8 |
| 13 rules for writing | 10 | 9.1 |
| the same 13, plus 17 for reviewing | 10 | 9.0 |

Thirteen rules lifted the score with nothing enforcing them. Adding the other 17 changed nothing, mostly because the runs were already passing nearly every check. That doesn't make those 17 rules checks. A rule becomes a check only when a script can decide it, whatever it does to the score. Still, a reasonable person looking at this table stops here.

But one rule hardly held. It said that when a setting is missing, the program must stop and say so, not quietly carry on with a backup value written into the code. Across the 20 runs that had the rule, 19 kept the backup anyway. A **check** is code that judges the output, and it gives the same verdict for the same input with no model involved. It catches that backup value in every run.

<Diagram id="agents-check" />

Checks come from failures, not from what looks correct.

1. Something goes wrong.
2. It becomes a rule, with the case that caused it.
3. Someone asks whether a script can decide it.
4. If one can, someone other than the builder writes the check and proves it twice, by failing on the bad case and by passing on the good examples.

Without the first proof, nobody knows the check can catch anything. Without the second, it fires on good work too, and people learn to ignore it. I once found a check that had never been seen failing for the right reason. The test for my name detector (a model that finds personal names before anything is shared) printed a score of zero when it couldn't reach the model at all. It had judged nothing, but zero reads as "judged everything and found nothing". The fix is filed, and when the test can't run, it will say so with its own exit code.

```
$ pii_eval.py                     # every model call refused (shortened)
pii eval: FAIL  recall 0.000      ← today: a score of zero
pii eval: could not run           ← the fix: unknown, not zero
```

This is where the foundry matters most, because **the builder never edits the judge**. A designer whose layout puts two wires too close together doesn't get to widen the rule. They move the wires.

<Diagram id="agents-foundry" />

If they could edit the deck, each rule would loosen exactly as far as their layout needed, and the deck would stop meaning anything. An agent that can edit a check is rewarded for loosening it in the same way, so checks belong in their own folder that the agent may not touch. Today that's only an instruction in my playbooks, and the hook that would block the edit isn't built yet. The waiver carries over too. When a check can't be met, the agent doesn't work round it. It records the case, and a person signs off.

The check judges. The agent still needs something to build with.

## The kernel the agent builds with

What the agent builds with is its **kernel**, a set of ready-made functions, each a named piece of code that does one job. Take my slide playbook. Without a kernel, the agent would write fresh code for every slide, and every deck would come out a little different. With one, it decides what each slide should say and calls the function for that kind of slide, and the function lays it out in my design. Like a check, a kernel gives the same result for the same input every time, which is what *deterministic* means. The two differ in direction. The kernel builds, the check judges, and a review by a fresh reader answers what neither can decide.

A kernel can run to thousands of lines. My slide playbook holds 2,866 lines of code against 712 lines of words. Reading all of it would cost the agent time and tokens, the units a model reads and is billed by. So the kernel opens with a **one-screen index**, one line per function saying what it does and how it goes wrong, like a menu in front of a recipe book. The agent reads the menu, then calls a function by name, and the function's code runs on the computer. The model never reads that code, so the work done inside it costs no tokens at all. Here's what such an index looks like, simplified.

```
title_slide(title, subtitle)     the opening slide, in my design
points_slide(heading, points)    at most 5 points, a sixth is refused
chart_slide(heading, numbers)    picks the chart from the numbers' shape
```

Each line also carries the trap that caught an agent before, written where the next agent would fall into it.

<Diagram id="agents-kernel" />

Some output needs a little randomness, such as where to scatter a pattern in a figure. A **seed** is a number fixed in advance that decides those choices, so the same inputs and the same seed always give the same output. Nothing in the kernel reads the clock or rolls dice of its own. Then pieces can be built in any order, side by side or again, and come out identical, which is what makes the work repeatable rather than merely similar.

## Where taste comes from

Taste is knowing which option is right before you can say why. People build it by seeing a lot of good and bad work, and a model doesn't have it. Nothing in this article gives it any. What a playbook can hold is my taste, written down as far as it goes, so that every run lands in the same style.

Drawing figures looks like the last thing you could hand to rules, and the best example I've found is [Hairline](https://github.com/lucasmarkes/hairline), an open-source playbook for drawing figures by Lucas Marques. I like its principles and have adopted them. In plain terms it does four things.

- It draws with one 24 KB file of building code, with an index of about 80 lines on top, so every figure uses the same pieces.
- Its checks run on every figure and every revision, and the agent isn't allowed to edit them.
- It keeps only 10 rules that still need judgment, so the model's attention goes where it's needed.
- Its examples set the bar in numbers, such as a figure filling about 36% of its frame.

It also has a short table of temptations, written the way the agent would think them.

| If you catch yourself | Do this instead |
|---|---|
| reaching for a colour, a fill or a glow | make one existing line the highlighted one |
| editing the building code or the test page to make something work | the figure is wrong, so change the figure |
| letting in a second idea | cut it, because one figure holds one idea |

I tested it on the same request a handful of times. Asked for a drawing for the documents section of my site, the model alone drew the same stack of paper cards five times out of five, in new colours each run. With Hairline, five runs drew four different objects in one style, and its checks caught faults the model alone never reported, such as a drawing filling only 24% of its box. On my own dark page, though, its drawings nearly vanished, because the taste a playbook carries is its author's.

That's why it repeats. Two runs draw with the same pieces, pass the same checks and are measured against the same examples, so they land in the same style even when the model chose differently along the way. My own site works the same way. Its playbook for drawing figures holds 13 rules, from which colours a figure may use to how long its code may be, and a script checks every figure against them before it ships.

## The playbook

Put the steps, the rules, the kernel, the checks and the examples for one job in one folder, and you have a playbook. It's opened whenever that job comes up, and it's kept under version control (a history of every change, which can be rolled back) with its agent.

<Diagram id="agents-playbook" />

This is the folder layout my playbooks use.

```
explain-oom/                 one job: explain an out-of-memory crash
├─ SKILL.md      the steps, when to ask, how to hand over
├─ RULES.md      craft rules: judgment only
├─ LOOK.md       evidence to produce, and the questions a reviewer answers
├─ tools.md      which of the agent's tools it uses, with their traps
├─ kernel/       code it builds with
├─ checks/       code that judges, which the agent may not edit
└─ examples/     a few good and bad outputs: the quality bar
```

Three rules make a playbook behave the same way every run.

- **Its description is a trigger.** It says only when to use it ("Use when a job died for lack of memory and someone asks why"), never a summary of its steps. That fixes the second failure where it starts.
- **It checks itself before it hands over.** Its last steps run the checks, answer the reviewer's questions with cited evidence, and say what wasn't verified.
- **It hands over in a fixed form.** That means one of four statuses (done, done with concerns, blocked, needs context), the full report in a file, and a reply of under fifteen lines that names the file and what wasn't checked.

Where a rule sits matters as well. A rule that matters in one step goes in that step rather than the main list, because a rule that doesn't apply still costs attention.

## The agent

An **agent** owns several playbooks, keeps what it learns between runs, and is the name on the work. That identity has four parts. Its **scope** is what it's responsible for, its **memory** is what it alone writes, its **permissions** are what it may do, enforced outside the model, and its **accountability** is the person who owns it and authorises what it does. Today my agents have the first two. They still run with my permissions, and the records name me, not the agent.

<Diagram id="agents-hierarchy" />

An agent starts every session blank, like a contractor who forgets everything overnight, and what isn't in a file is gone. So each agent keeps a **memory index**, a short file like a book's contents page, with one line per thing it has learned, each pointing to a note with the detail. The index is read at the start of every session, and the agent opens only the notes the task needs. Only the agent itself writes to it.

Whether to make a new agent at all is the first failure again. Go down this list and stop at the first choice that works.

| Choice | Use it when |
|---|---|
| 1. A plain script | The steps and the answer are fixed by the data |
| 2. A fixed sequence with one model step | The steps are fixed, and one step needs judgment or language |
| 3. A new playbook in an existing agent | Same owner, same data, same permissions, and a new procedure |
| 4. A new agent | A new boundary: what it may do, what data it reads, who owns it, who it serves |

So a new topic is a playbook, and a new agent needs a new boundary.

The agents that earn choice 4 come in two kinds. A **resident** lives in one project's code and keeps going between sessions, and an event starts it, such as a message, a schedule, a hook or a person. A **shop agent**, a front-end agent say, has a craft but no project. It sets up shop where it's called, brings its own playbooks and memory, and takes its context from the project it's working in, the way a contractor brings their craft and takes the brief from you.

## Workers, the orchestrator and one run

A good resident works like a good lead. It decides how to split the work, judges what comes back and remembers what was learned, and it leaves the bulk of the building to others, because doing everything itself is how it drowns. That's what workers are for. A **worker** lives for one brief. The brief goes in, a result comes out, and the worker ends. It has no memory of its own and works under its parent's identity. Between the resident and its workers sits the **orchestrator**, and I first pictured it as another agent. It doesn't need to be one. Starting workers, waiting, collecting, retrying and enforcing limits are fixed steps, so by the ladder they belong in a script. What to split, what to accept and what to remember stay with the resident.

<Diagram id="agents-orchestrator" />

I ran this once, as an experiment, with the agent that files incoming feedback into one of my projects as the resident. It gave four workers three messages to file and a set of agreed rule changes. Each brief named the only files that worker could edit, so no two workers touched one file. Workers couldn't save changes to the project's history or edit the shared log, and they answered in a fixed form with room for "problems with my brief" and "what I didn't verify".

```
workers        4, started at once by one script
run time       215 seconds
tokens         289,186 across the workers, 62 tool calls
               (a flat monthly plan, not billed per token)
conflicts      0: every file had one owner
brief problems 15 reported, several real
not verified   15 reported
requests       30 for files no worker owned, all left for the resident
```

The workers were fast and honest, and one caught two items sharing an id that the resident had missed. Still, the cost moved up. The resident still had to apply 30 requests for shared files, split one change into two saves to the history by hand because workers couldn't save, and catch what no brief had asked about. One run is one case, but it already shows what the orchestrating script needs. Each file is owned by one worker, shared files stay with the resident, every brief is checked against the files it names before the run, each request is marked "needed" or "nice to have", and the checks run before anyone reads the prose.

This is why I always cut work into narrow vertical slices before handing it to workers. A vertical slice is a thin piece that goes all the way through, from the ask to something that can be checked on its own. Slicing well is the hard part, and it's the resident's job and mine, so the resident gets the best context and the strictest review, and each worker gets the narrowest brief.

Put together, a run goes from request to result in the same order every time. The table puts rules I already follow in one sequence, though the sequence itself isn't a written playbook yet. A script holds a step when its answer is fixed, a model when it needs judgment, and a person when it's accountable or can't be undone.

| Step | What happens | Held by |
|---|---|---|
| 1. Start | A hook, schedule, message or review request starts the resident | script |
| 2. Frame | A vague ask gets five questions first, each with a predicted answer | resident, then a person confirms |
| 3. Slice | The work is cut into narrow pieces, each with a brief that names its files | resident |
| 4. Dispatch | Workers start, limits are enforced, results are collected | script |
| 5. Build | Each worker builds with the kernel, inside its own files | worker |
| 6. Check | Checks run on the output, and the reviewer's questions are answered with cited evidence | script, then worker |
| 7. Hand over | Status, report file, short reply, what wasn't verified | worker |
| 8. Review | A fresh reader with no build context answers what the checks can't | reviewer |
| 9. Record | Conflicts and guesses are written down as what, why and cost if wrong | resident |
| 10. Accept | Any of the five stops below waits for a person | person |

The five framing questions are what this must prove and to whom, the one moment that has to land, what we won't do, the smallest version, and how we'll know it's done. Everything else in a run is decided, written down, and the run carries on. Only five things stop it to wait for a person.

1. A step that can't be undone.
2. A step that touches security.
3. A change that leaves the workspace, such as publishing or sending changes to a shared server.
4. A plan so broken that every path is a guess.
5. Spending past an approved limit.

## Rules above any one agent

Workers, residents and shop agents all follow some of the same rules, so those rules live above any one agent, in one shared set per kind of work, such as writing code or drawing diagrams. A rule lives at the level where its decision is made.

<Diagram id="agents-rule-levels" />

The parts also combine. One playbook can hand its result to the next, so a playbook that plans a deck feeds the one that builds it in PowerPoint. A playbook can call another inside one of its steps, so the deck builder calls a chart playbook for every chart. The agent's own rules sit above all of its playbooks. And an **eval** tests the whole agent the way a check tests one output, with fixed tasks whose answers are known, run again after every change to its prompt, its model or its tools. I don't run evals on every playbook yet, so that last part is still design.

<Diagram id="agents-chain" />

Each rule also says who holds it, which is the writer while writing, a reviewer with fresh eyes, or a check. My earlier agent framework, synapse, shows why that matters. When I audited it, its rules lived in one place and its checks in another. They had drifted, and the project failed its own checker with 114 errors, with two versions of the same rule in force at once.

## Does each part hold up?

Every part above gets a test of its own. The article opened by asking "why?" until each failure reached a cause. Run it the other way, from each part down to the failure it exists to stop, and a part should land on something that happened, or at least on a named risk, and say what would show it's wrong.

| Part | Lands on | Event or risk | What would show it's wrong |
|---|---|---|---|
| Check | 19 of 20 runs ignored a rule in the prompt | event | a check that never fails on a planted break |
| Checks kept apart from the kernel | a builder who can edit the judge loosens it | risk | an agent's edit that reaches `checks/` |
| Description as a trigger | the right procedure isn't called, or its steps get skipped | event | a playbook never called, or called and skipped |
| Agent split at a boundary | per-topic agents with their own copies of rules | event | two agents with the same permissions, data and owner |
| Orchestrator as a script | a model makes fixed steps vary | risk | a run whose limits or retries differ for the same input |
| Memory in files | about 17 agreed items with no row anywhere | event | a decision that exists only in a chat |
| Shared rules that say who holds them | synapse's rules and checks drifted apart | event | two agents citing different versions of one rule |

Five rows land on something that happened. Two land on a risk I reasoned my way to, and those are the two I'd doubt first.

Each part also has a way to move. A rule moves down into a check when a script can decide it, and it leaves when its case still passes without it.

Not all of this is proven either. Whether a resident holds up under real load is untested. Whether task difficulty matters more than the number of rules is an experiment written and not yet run, and the orchestrator rules come from one run.

## If you don't write code

I think there will be no such thing as low code or no code. Everyone will code, and an agent will type it for them. What you still need is the idea underneath, that a script gives the same answer every time and a model doesn't. Everything above moves work across that line, and you don't need to read code to do it. You need to ask for the right things, in this order.

1. **Say what done looks like before anything is built.** Answer the five framing questions, or confirm the agent's guesses at them. A wrong guess here costs days later.
2. **Ask "can a script decide this?" of every rule you give.** If it can, have a check written for it by someone other than the agent doing the work, and approve it yourself.
3. **Ask to see the check fail.** Have the work broken on purpose and watch the check catch it. A check you've never seen fail isn't a check yet.
4. **Keep two or three examples of good, and one of bad.** They're your taste, in a form checks and reviewers can measure against.
5. **Never accept "done" in words.** Ask for the check's output and the list of what wasn't verified.
6. **When it fails, ask for a rule with its case.** Not "be more careful", but a rule that names the failure, so the next run inherits it.
7. **Keep the decisions that can't be undone.** Merges, publishing, spending past a limit and anything touching security stay yours.

Here are steps 2 and 3 for someone in finance with an agent drafting supplier emails. "Every email names the purchase order" is a rule a script can decide, so a second agent writes the check, and it's shown failing before anyone trusts it.

```
you      > Can a script decide "every email names the purchase order"?
checker  > Yes: a PO number has a fixed form. Here is check_po.py,
           the drafting agent can't edit it.
$ check_po.py drafts/supplier-reminder.txt
FAIL  no purchase order number found          ← the check bites
$ check_po.py drafts/supplier-reminder-fixed.txt
ok
```

"Polite but firm" stays a rule, because no script can decide it, and your one good example email is what a reviewer measures it against. None of this needs you to read the code. It needs you to know which parts of your work are fixed and which need judgment.

## What to remember

- Each failure traced back to a decision that lived only in written instructions, so the fix is to give that decision to something that can hold it.
- A rule a script can decide belongs in a check, proved by watching it fail.
- The kernel builds and the check judges. What looks like the model's taste is a person's taste, written down as rules, code and examples.
- A playbook is one responsibility, and a new agent needs a new boundary (permissions, data, owner), never a new topic.
- An agent starts blank, so what it knows lives in files only it writes.
- Coordinating workers is a script's job, and a run stops for a person only at the five stops.
- Every part should land on a failure it stops, and say what would show it's wrong.
- If you don't write code, ask whether a script can decide it, then ask to see the check fail.

That's the foundry's bargain, made for agents. Nobody asks the designer to be careful. They get a deck they can't edit, and their judgment is kept for the architecture.
