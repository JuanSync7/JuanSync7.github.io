Most inference engines tell you how fast they are, and trnrt also tells you exactly where its own numbers stop being true.

## One model, one box, no GPU

[trnrt](https://github.com/RunanywhereAI/trnrt) is an open inference engine that serves a large language model on AWS Trainium2, the chip Amazon builds for machine learning instead of buying GPUs. The problem it solves is narrow and expensive. You want to run a very large open model with a very long context, you want to pay less per token than a GPU cloud bill, and the software for Trainium is far thinner than the software for GPUs.

Today it supports one model, GLM-5.3-Flash, a mixture-of-experts model with 320 billion parameters of which about 18 billion are used per token, and one machine, the `trn2.48xlarge` with sixteen Trainium2 chips. The scenario it is built for is a team running many coding agents at once against a model with a context of up to a million tokens. Those agents send long prompts that mostly repeat what they sent last time, so the engine keeps a cache of earlier prompts and routes each conversation back to the engine that already holds its prefix.

## How a request moves through it

A request arrives at a small router on port 8000 that speaks the OpenAI API, so any OpenAI client works by changing the base URL. The router keeps each session on one of two engines that share the box. Each engine splits the model across 32 logical cores on eight chips, which is called tensor parallelism. Before computing anything, the engine checks its prefix cache, a tree of earlier prompts stored as compressed pages in device memory, with a second tier in host memory for pages pushed out of the first.

The interesting part is decode, the step that produces one token at a time. The authors found that on this chip decode is not held back by memory bandwidth, the usual limit, but by many small instructions, kernel boundaries and waits on communication between cores. So they wrote one large fused kernel per half of each model layer, a megakernel, that keeps its working data in fast on-chip memory and does the communication inside the kernel.

All of this is compiled ahead of time. Five commands, run on any ordinary x86 machine, build every compute graph the engine will need, and the serving box only loads them. The README says this compile takes hours.

## What it takes to run

You need Docker, a `trn2.48xlarge` to serve on, a separate host to compile on, the model weights from Hugging Face, and the Neuron SDK at the version the image pins. The serve command runs the container privileged, on the host network.

The project is under the Apache 2.0 licence, had about 1,650 stars on GitHub when I checked, saw its first public release, 0.1.0, in early November, and was still being pushed to. It has a CPU test suite of close to a hundred files that needs no Trainium, lint and type checks in CI, and a tool that compares compiled graphs.

## Where it stops

The headline numbers come from the project's own runs of a public agent benchmark, measured on an earlier build. What makes the repo worth reading is how it handles that gap. The known-issues page says the current code matches the earlier build on all 157 compiled graphs and produces byte-identical output on 384 of 384 test requests. It then documents a shortcut in its sparse attention that can pick slightly different context blocks, measures how often that happens and how much it moves the model's output, and exposes counters so an operator can watch it. A CPU test that fails by a small margin is kept as a strict expected failure, so the suite breaks if it ever starts passing unnoticed.

The limits are real too. It runs one model, adding another means lifting assumptions the engine still makes, and past a certain load the host cache fills and throughput drops.

## Where I stand

On a first read I would not run this. I work with GPU serving, and I keep behaviour in config so that a change is simple. A box that supports one model, after an hours-long compile per model, is the opposite of that. The privileged container on the host network is the other reason. When in doubt about security I stay strict, and I would want to know exactly why it needs that much before giving it a machine.

What I would steal is the verification page. I believe correctness is the foundation and that a system I cannot explain is a system I should not trust. This repo writes down which claims were checked, against what, and which were not. The first thing I would do is read `tools/graph_equiv.py` and ask whether the same idea, recorded outputs from a known-good build compared byte for byte after every change, fits the configs I change on my own serving setup.

The question I cannot settle yet is whether non-GPU silicon is something I should follow closely or only note. Its cost table makes a case, at about four cents per million tokens on spot pricing, but that figure is theirs, not mine.

Verdict: study.
