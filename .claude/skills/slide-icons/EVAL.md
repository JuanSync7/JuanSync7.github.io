# Evaluate the playbook

This is a maintainer procedure. Output checks and behavioral skill evaluation
have separate results. A green icon does not establish that the skill generalizes.

1. Preserve the baseline skill/engine revisions before editing. Prepare realistic
   unseen slide requests and fit criteria without showing the candidate skill to
   the case writer. Include reuse, a genuine mismatch requiring creation, a plural
   collection, a new view description and pressure to skip review or edit checks.
2. Run fresh baseline and candidate sessions against the same briefs. Preserve
   each prompt, artifact, loaded files, tool evidence, decisions and unknowns.
   A failed run or blocked capability is evidence; do not remove it from totals.
3. Run deterministic artifact and ownership checks. Judge recognition/fit with a
   separate reviewer using shuffled labels. Do not tell the reviewer which label
   is preferred or pre-judge permissible findings.
4. Compare completion, fit, applicable-rule loading, forbidden checker edits,
   verification and measured interventions/effort. Missing measures stay unknown.
   Several successful trials are bounded evidence, not universal reliability.
5. Preserve the before/after hashes, rule-to-case results, reviewer evidence and
   limits in `docs/design/slide-icons/evaluation/`. Re-run affected cases after
   rule edits. Run the whole behavioral suite on the final skill revision.
6. Release only the assessed revision. A later task records actual use separately.
   Vault proposal/review/release records and rule-package adoption remain separate;
   do not claim this repository's report registered or approved them automatically.

Configured case set and runner instructions live under `astro/scripts/slides/evals/`.
Fresh agents require explicit session authorization when the host requires it.
Without independent runs, mark that lane pending; never substitute role-play.

Fixed user corrections are output regressions, not held-out behavioral trials. Fresh blind trials must also cover choosing a semantic component instead of a convenient edge, leaving a glyph neutral, and including every member of an equivalent functional set. Keep judgments about meaning separate from exact rendering fidelity. Do not reuse the fixed examples as evidence of generalization.
